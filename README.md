# k8s-platform-lab

Лаборатория эксплуатационной обвязки сервиса в Kubernetes: пробы, метрики, автоскейлинг и деплой без потери запросов — на локальном кластере kind, одной командой.

Приложение здесь намеренно маленькое. Интересна не бизнес-логика, а то, что вокруг неё: как под сообщает о своей готовности, что происходит с запросами в полёте при обновлении, по какой метрике считается автоскейлинг и почему именно по ней.

```bash
make up          # кластер, ingress, metrics-server, деплой
curl localhost   # {"app":"k8s-platform-lab","version":"dev","instance":"my-app-..."}
```

## Стек

| Компонент | Версия / выбор |
|---|---|
| Приложение | Python 3.12, FastAPI, uvicorn, prometheus-client |
| Кластер | kind — 1 control-plane + 2 worker, порты 80/443 проброшены на хост |
| Пакетирование | Helm-чарт собственной сборки, без зависимостей |
| Ingress | ingress-nginx `controller-v1.15.1` |
| Метрики для HPA | metrics-server `v0.9.0` |
| Локальный мониторинг | Prometheus + Grafana через docker-compose |

## Требования

`docker`, `kind`, `kubectl`, `helm` 4.x. Порты 80 и 443 на хосте должны быть свободны.

## Команды

```bash
make help        # список целей
make up          # всё с нуля до рабочей ссылки http://localhost/
make deploy      # пересобрать образ, загрузить в кластер, обновить релиз
make test        # helm test — пять проверок по живым эндпоинтам
make load        # нагрузка: разогревает HPA и наполняет графики
make lint        # helm lint + рендер шаблонов
make down        # удалить кластер
```

`make up` идемпотентен в части кластера: если он уже существует, цель это сообщит и не станет пересоздавать.

## Эндпоинты

| Путь | Назначение |
|---|---|
| `GET /` | версия и имя инстанса — видно балансировку между репликами |
| `GET /healthz` | liveness: 200, пока жив процесс; зависимости не проверяет |
| `GET /readyz` | readiness: 503 во время прогрева, затем 200 |
| `GET /metrics` | метрики в формате Prometheus |
| `GET /api/work?ms=N` | жжёт N мс CPU — чем нагружать HPA и пробивать SLO |
| `POST /admin/ready` | ручное переключение готовности для chaos-тестов; выключено, пока не задан `ADMIN_TOKEN` |

## Что демонстрирует чарт

Каждый пункт здесь — отдельное решение, которое можно объяснить, а не строка из скаффолда.

**Три пробы с разной семантикой.** `startupProbe` даёт приложению до минуты на запуск и на это время блокирует `livenessProbe`, чтобы медленный старт не превращался в цикл рестартов. `livenessProbe` смотрит только на процесс. `readinessProbe` отражает реальную готовность: пока идёт прогрев, под не получает трафик, хотя уже запущен.

**Деплой без потери запросов.** `preStop` с паузой и `terminationGracePeriodSeconds: 30` дают ingress-контроллеру обновить апстримы, пока uvicorn ещё отвечает: SIGTERM и удаление из Endpoints происходят параллельно, и без этой паузы часть запросов в полёте теряется.

**Перезапуск при правке конфигурации.** Хеш отрендеренного ConfigMap лежит в аннотации pod-шаблона (`checksum/config`). Deployment катит поды только при изменении своего шаблона, поэтому без такой аннотации правка ConfigMap осталась бы незамеченной: переменные окружения впечатываются в контейнер один раз, при создании.

**HPA на `autoscaling/v2`** по утилизации CPU относительно `requests`. Отсюда требование: `resources.requests.cpu` обязателен, иначе проценты считать не от чего.

**PodDisruptionBudget** с `minAvailable: 1`. Защищает от вытеснения через Eviction API — `kubectl drain`, обновление нод, descheduler. От прямого `kubectl delete pod` не защищает, и это не недоработка, а область действия механизма.

**Распределение реплик** через `topologySpreadConstraints` по `kubernetes.io/hostname`, чтобы обе реплики не оказались на одной ноде.

**Контейнер под ограничениями:** не root (uid 10001), read-only корневая файловая система, `allowPrivilegeEscalation: false`, сброшены все capability, `seccompProfile: RuntimeDefault`. Чарт проходит встроенный профиль Pod Security Admission `restricted` — проверяется так:

```bash
kubectl label --dry-run=server --overwrite ns my-app \
  pod-security.kubernetes.io/enforce=restricted
```

Отсутствие предупреждений означает, что ни один под в namespace профиль не нарушает.

**`helm test` проверяет поведение, а не наличие.** Пять проверок: `/healthz` и `/readyz` отдают 200, `/metrics` содержит `app_ready` и гистограмму латентности, `/` возвращает JSON с версией.

## Метрики и SLO

Экспортируются `http_requests_total`, `http_request_duration_seconds`, `app_ready`, `app_build_info`.

Два решения, которые стоит отметить:

- Лейбл `path` — **шаблон роута**, а не сырой URL. `/api/work?ms=50` и `/api/work?ms=900` попадают в одну серию. С сырым путём любой клиент мог бы бесконечно наращивать кардинальность и положить Prometheus.
- Граница гистограммы стоит ровно на `0.2`, потому что целевой SLO — p95 латентности `/api/*` ниже 200 мс. `histogram_quantile()` интерполирует внутри бакета, поэтому порог, не совпадающий с границей, даёт число, которое нельзя защищать.

`scripts/generate-load.sh` гонит смешанный трафик, сам читает итоговый p95 из Prometheus тем же запросом, что стоит в панели Grafana, и возвращает ненулевой код, если SLO пробит.

Дашборд `monitoring/grafana/dashboards/app-overview.json` — «App overview»: готовые инстансы, p95, доля ошибок, версия, частота запросов по роутам, перцентили латентности, ответы по статусам.

## Честные ограничения

Сознательные упрощения, а не недосмотры.

- **metrics-server запускается с `--kubelet-insecure-tls`.** kubelet в kind отдаёт метрики по HTTPS с самоподписанным сертификатом, который кластерный CA не подписывал. Правильное решение в настоящем кластере — `serverTLSBootstrap: true` в конфигурации kubelet и одобрение CSR; флаг здесь лабораторный срез.
- **Версия Kubernetes выходит за матрицу поддержки ingress-nginx.** `controller-v1.15.1` протестирован на 1.31–1.35, а кластер поднимается на образе ноды, который kind предлагает по умолчанию. На практике работает; для строгой воспроизводимости образ ноды стоит запинить явно.
- **Контроллер ingress прибивается к control-plane патчем.** Манифест kind-провайдера больше не использует метку `ingress-ready`, а `hostPort` работает только на той ноде, где проброшены порты. Без патча контроллер может уехать на воркер, и `localhost` перестанет отвечать.
- **Потолок автоскейлинга — 4 реплики, и это не круглое число.** У `topologySpreadConstraints` поле `nodeTaintsPolicy` по умолчанию равно `Ignore`, поэтому control-plane считается доменом распределения, хотя поды туда не попадают из-за taint. При `maxSkew: 2` это даёт не больше двух подов на воркер, то есть четыре на двух воркерах.
- **Мониторинг пока только в docker-compose.** Prometheus и Grafana поднимаются рядом с приложением локально; в кластере их нет.

## Структура

```
app/                     приложение: пробы, метрики, генератор нагрузки на CPU
charts/my-app/           Helm-чарт: Deployment, Service, Ingress, HPA, PDB,
                         ConfigMap, ServiceAccount, helm test
configs/cluster.yaml     кластер kind: 3 ноды, проброс портов 80/443
monitoring/              Prometheus и Grafana для локального запуска
scripts/generate-load.sh нагрузочный профиль с проверкой SLO
Dockerfile               образ на python:3.12-slim, запуск от uid 10001
docker-compose.yaml      приложение + Prometheus + Grafana без Kubernetes
Makefile                 все операции над кластером и релизом
```
